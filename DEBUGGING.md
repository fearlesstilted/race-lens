# Диагностика live-режима за 60 секунд

Цепочка данных — всегда одна:

```
фид F1 → файл записи → парсер → движок → API/стрим → браузер
```

Любое «пусто/не работает» = вопрос «какое звено молчит?». Проверка по звеньям,
сверху вниз — где первая аномалия, там и проблема:

| # | Звено | Команда | Норма |
|---|-------|---------|-------|
| 1 | Запись идёт | `ls -la backend/fixtures/_capture_*` | размер файла растёт между запусками |
| 2 | Парсер даёт события | `curl -s localhost:8000/api/live/status` | `events_total` растёт, `consecutive_failures: 0` |
| 3 | Стрим отдаёт кадры | `curl -sN "localhost:8000/api/live/stream?tick_s=1" \| head -c 400` | JSON с `classification` и `drivers` |
| 4 | Браузер получает | F12 → Network → `stream` → Response | data-строки капают |

Формула баг-репорта: **звено + факт + ожидание.**
«events_total растёт, а таблица пустая» — этого достаточно, дальше дело техники.

Нюансы, которые уже кусались:
- Между сегментами квалы / до формейшна фид молчит — `new_last_poll: 0` это норма, не баг.
- F5 в браузере подхватывает бегущую сессию; второй START вернёт 409 — так и задумано.
- STOP до конца сессии обрывает запись. Запись = сырьё для replay-фикстуры, береги её.
